# Running Overture's STAC catalog through Portolan

Notes from a working session on 2026-08-29. Everything below was run against the live
`stac.overturemaps.org` catalog and the published `2026-08-19.0` Parquet.

**Portolan** is a profile layered on top of STAC: same JSON, stricter rules about what a
catalog must document before it counts as usable. **rashid** is its validator. Neither is a
STAC validator — that distinction turns out to matter, and it's the first finding below.

---

## Headline

| | |
|---|---|
| Overture's catalog against **STAC** validation | **passes** |
| Overture's catalog against **Portolan** (rashid) | 1135 errors, 3961 warnings across 1009 files |
| A rebuilt places+buildings demo | **3 errors**, all thumbnails |

Two real bugs surfaced along the way, one already known, one not. Plus a data-quality
finding about buildings that changes how the data should be styled and described.

---

## Setup

The `claude` CLI isn't installed on this machine (desktop app only), so
`claude plugin marketplace add portolan-sdi/portolan-skills` wasn't available. The
10 skills were installed by hand into `~/.claude/skills/` instead — they're plain
markdown plus a few Python helpers, no hooks or MCP servers. They register as
`/portolan-bootstrap` etc. in a new session.

Toolchain, in a scratch venv:

```bash
uv venv portolan-venv
uv pip install --python portolan-venv/bin/python \
  'rashid>=0.1.8,<0.2.0' stac-check portolan-cli
```

**The rashid version pin is not optional.** This machine already had rashid 0.1.6 on
PATH. Per the `portolan-migrate` skill, releases 0.1.5–0.1.7 wrongly reject a conforming
v0.2.0 catalog, and 0.1.4 silently under-reports several rules. Running the version that
was already installed would have produced confidently wrong results. Check what you're
invoking: `portolan check` uses the CLI's bundled rashid, a bare `rashid check` uses
whatever is on PATH, and they're routinely different.

Two more practical notes:

- `rashid check` takes a **local catalog directory**, not a URL, and not a
  `collection.json`. Mirror the catalog first.
- `--data` is **on by default** and reads every asset's bytes. Against Overture that
  means pulling Parquet from S3, and the run never finishes. Use `--no-data`.

## Which skill applies

Chris suggested `portolan-bootstrap`. Its own opening text redirects away from this case,
twice — to `portolan-migrate` when a catalog already exists, and to `git-backed-catalog`
when metadata lives in a repo with CI. Bootstrap is data-first: extract from a source,
convert, push to a bucket. Overture's catalog already exists and is generated by Python in
`OvertureMaps/stac`, so the migrate path fits: audit what's there, repair the metadata,
leave the data alone.

Worth feeding back to Chris — the redirect worked exactly as designed, which is a point in
the skills' favour, but the bootstrap recommendation was the wrong starting point for this
repo.

## The audit

15 type collections across 6 themes in the `2026-08-19.0` release, 987 items.

| Field | Present | Notes |
|---|---|---|
| `title` | 15 of 15 | but 5 are raw slugs (`land_cover`) |
| `description` | 15 of 15 | all ~30 chars: *"Overture's building collection"* |
| `providers` | 0 of 15 | |
| `keywords` | 0 of 15 | |
| assets on collections | 0 of 15 | PMTiles is a `rel="pmtiles"` link on the *theme catalog*, not an asset |
| `table:columns` with a type | 0 of 217 | |
| `table:columns` with a description | 0 of 217 | |
| README.md / AGENTS.md | 0 | |
| thumbnails | 0 of 15 | |
| styles | 0 of 15 | |

The temporal extent is `[[None, None]]` on every collection. That is **correct** — Overture
has no temporal data, and that's the spec-valid way to say "unbounded". It shows up on the
migrate skill's generic checklist as a gap; it isn't one here.

### Bug 1 — collection bounding boxes (already filed)

This is [OvertureMaps/stac#121](https://github.com/OvertureMaps/stac/issues/121), filed by
gadomski, assigned to jjcfrancisco. The audit adds scope and a line number.

STAC requires `bbox[0]` to be the overall extent of the collection. It isn't wrong here so
much as **missing** — the bbox count equals the item count exactly, so the list is just the
per-item bboxes with no union prepended.

```
addresses/address
  declared bbox[0]: [-176.87, -90.0,  -74.35, 19.55]
  actual union:     [-166.59, -54.94,  178.55, 78.34]
```

**11 of 15 collections affected.** The other 4 have exactly one item, so `bbox[0]` is
trivially correct. Cause is `src/overture_stac/overture_stac.py:331`:

```python
bboxes=[i.bbox for i in local_type_collections[type_name]]
```

Neither validator catches this — it's a semantic rule JSON Schema can't express, and rashid
doesn't check it either. That's likely why it went unnoticed.

### Bug 2 — item bboxes outside WGS84 (not filed)

Four items in `base/land_cover` have longitudes past the antimeridian:

```
base/land_cover/00000   [-180.00022888183594, ...]
base/land_cover/00016   [-180.00022888183594, ...]
base/land_cover/00083   [...,  180.00022888183594, ...]
base/land_cover/00127   [...,  180.00022888183594, ...]
```

Overshoot is 0.00022888°, about 25 m at the equator. GeoJSON (RFC 7946) and STAC both
require longitude within ±180. stac-check misses it because JSON Schema doesn't constrain
the numeric range; rashid catches it as `PTL-BBX-001`.

The generator isn't inventing this — `overture_stac.py:224` reads the bbox straight from the
GeoParquet `geo` metadata, so the land_cover Parquet's own metadata makes the claim.
Clamping in the STAC generator would make the validator pass while hiding an upstream data
issue. Better raised with whoever produces land_cover. Low stakes either way at 25 m.

### Bug 3 — nothing, but worth knowing

`places/place` and `addresses/address` are licensed `other` with a link to the attribution
page; the rest carry real SPDX identifiers. Not necessarily wrong, but licence is a field
the skill says never to change without the publisher confirming, so it was left alone.

## The buildings finding

This one isn't a bug, and it's probably the most useful thing here.

Building attributes are **very** sparse. Measured across 39,680,766 rows spanning 8 of 512
partitions (0, 64, 128, 192, 256, 320, 384, 448) — a spread, not one partition:

| Column | Populated |
|---|---|
| `subtype` | 1.62% |
| `class` | 1.56% |
| `names` | 0.26% |
| `height` | 0.11% |
| `roof_shape` | 0.027% |

Reproduce with:

```sql
INSTALL httpfs; LOAD httpfs;
SELECT count(*) AS total,
       round(100.0 * count(subtype)    / count(*), 2) AS subtype_pct,
       round(100.0 * count(class)      / count(*), 2) AS class_pct,
       round(100.0 * count(height)     / count(*), 2) AS height_pct,
       round(100.0 * count(roof_shape) / count(*), 3) AS roof_shape_pct,
       round(100.0 * count(names)      / count(*), 2) AS names_pct
FROM read_parquet('<any building partition href>');
```

Consequences:

1. **The obvious style is a lie.** "Colour buildings by subtype" paints ~98% of the world in
   the fallback colour while showing a 13-entry legend. The Portolan styling guide calls this
   the most common visible defect in a new catalog, and it's why the demo's default buildings
   style is a single colour rather than a choropleth.
2. **Attribute coverage tracks OpenStreetMap density, not building density.** Any analysis
   conditioned on `height` or `class` is working with a small, geographically biased subset.
   That belongs in the collection description, and now is.

Places, by contrast, are attribute-rich: `basic_category` is populated on 96.3% of rows in
partition `00000`, and `confidence` spreads across the full 0–1 range.

## The PMTiles zoom finding

The tiles at `tiles.overturemaps.org` are linked from each theme catalog as
`rel="pmtiles"`. Reading their headers and metadata directly over range requests:

| Archive | Vector layers | Layer zoom range |
|---|---|---|
| `places.pmtiles` | `place` | **14–14** |
| `buildings.pmtiles` | `building` | 4–14 |
| | `building_part` | 8–14 |

**Places tiles exist only at zoom 14.** The archive header advertises zoom 0–14, but
the lowest tile id in the root directory is 94,968,953, and zoom 14 begins at
89,478,485 — so there is genuinely nothing below z14. Buildings starts around z4
(lowest tile id 300, z4 begins at 85).

Consequence: anyone opening Overture places in a STAC or Portolan browser at a default
world view gets an empty map. It only renders once you are zoomed to roughly
neighbourhood level. This is also why a world-extent thumbnail for places would come out
blank — the "thumbnail shows basemap only" defect, caused by the tiles rather than the
style.

Worth confirming with whoever builds the tiles as to whether z14-only is deliberate.

## What got built

A standalone demo catalog covering `places/place`, `buildings/building`, and
`buildings/building_part` — 3 collections, 529 items. It **re-describes** Overture's data;
every asset href still points at Overture's own AWS and Azure buckets. Nothing is re-hosted
or modified.

Why a separate catalog rather than a partial adoption of the production one: rashid resolves
the profile schema from the **root** catalog and then validates every object against it. Declare
the profile at Overture's root and the 12 non-migrated collections all light up. A separate
catalog gives a clean run to look at; the group can then decide about the other 12.

Contents:

- **63 columns documented** with a type and a description (17 places / 24 building / 22 part).
  Descriptions are quoted or condensed from `docs.overturemaps.org/schema/reference/`. Types
  are read from the published Parquet footers with DuckDB `DESCRIBE` — not guessed.
- **12 markdown files** — README.md and AGENTS.md for all 6 catalogs and collections.
- **14 SQL recipes** in the AGENTS.md files, including the buildings↔parts join on
  `building_id`. Every one was executed against the published data; two early versions
  returned zero rows because I'd written London examples against a partition covering the
  Americas, and were rewritten.
- **8 MapLibre styles**, every `match` and `step` branch corresponding to a value actually
  measured in the data.
- `providers`, `keywords`, human-readable titles, the Portolan schema URI, `rel:describedby`
  and `rel:agents` links, titles on all 529 item links, and a corrected overall bbox.

### Result

```
before (places+buildings, as published):  565 errors, 2118 warnings
after  (rebuilt demo):                      3 errors, 2117 warnings
```

The 3 remaining errors are all `PTL-VIZ-001` — each collection needs a real PNG thumbnail.

**Attempted and parked.** chiitiler 1.23.2 installs cleanly from npm (372 packages) but its
`tile-server` subcommand starts, stays alive, and never binds a port, with no error on
stdout or stderr even under `-D/--debug`. Local port binding works in the same shell
(a plain `python3 -m http.server` answers immediately), so this is chiitiler failing
silently rather than an environment restriction — most likely its MapLibre GL Native
dependency failing to load headless on macOS arm64. The package ships no `bin` entry
either, so `npx chiitiler` does not resolve; it has to be run as
`node node_modules/chiitiler/dist/cli.js tile-server`.

Worth noting for whoever picks this up: the framing matters more than the renderer, and
the `place` layer's z14-only tiles (above) mean a places thumbnail has to be a
neighbourhood view. A world-extent frame renders empty no matter what the style says.

The 2116 remaining warnings are `PTL-AST-003`: every asset should carry `file:size` and
`file:checksum`. Adding those for the style files was easy; doing it for 1058 remote Parquet
assets means a HEAD request each, which belongs in the generator rather than a one-off script.

### Negative control

A clean validator run proves nothing until you've seen it fail. Three violations were planted
in a copy — removed the Portolan schema URI, emptied `providers`, deleted the `rel:agents`
link — and all three fired:

```
error  PTL-CNF-001  1x  catalogs and collections must declare the versioned Portolan schema URI
error  PTL-FIL-002  1x  AGENTS.md must be linked with rel:'agents' and type text/markdown
error  PTL-PRV-001  1x  every collection needs at least one provider with the producer role
```

## The generator changes (the STAC-hygiene pile)

Separate from the Portolan question, four changes went into
`src/overture_stac/overture_stac.py`. All are plain STAC improvements, wanted by both
validators, and independent of whether Overture adopts Portolan.

1. **Human-readable collection titles** — a `TYPE_TITLE_MAP` alongside the existing
   `TYPE_LICENSE_MAP`, so `land_cover` renders as "Land Cover" and `segment` as
   "Transportation Segments".
2. **`providers`** — Overture Maps Foundation with producer, licensor, processor, and
   host roles.
3. **`keywords`** — `["overture", <theme>, <type>]`.
4. **`table:columns` carries a type** — read from the Arrow schema the generator already
   holds, so `{"name": "confidence"}` becomes
   `{"name": "confidence", "type": "double"}`. No new I/O.
5. **Titles on item links** — read from the item id, since pystac links hold the Item
   object until hrefs are normalized.

Measured on the same debug-mode catalog, generator at HEAD versus with the changes:

```
before:  179 errors, 153 warnings across 59 files
after:   127 errors, 148 warnings across 59 files
```

| Rule | Before | After |
|---|---|---|
| `PTL-TTL-003` every child and item link must include a title | 37 | **0** |
| `PTL-PRV-001` every collection needs a producer provider | 15 | **0** |
| `PTL-TTL-002` titles must be human-readable (warning) | 5 | **0** |

Everything still failing is either Portolan profile adoption (README/AGENTS.md, schema
URI, thumbnails) or the land_cover bbox. `stac-check` on a generated collection passes
with an empty best-practices section, where before it flagged the missing link titles.

Full test suite passes, 62 tests — including the 30 end-to-end tests that only run once
`tests/setup_test_catalog.py` has built a catalog against real S3. Two existing tests
asserted the old behaviour (`title == "place"`, `table:columns` without types) and were
updated.

**Note on `uv.lock`:** commit `3b7385e` bumped `pyproject.toml` to 1.4.0 without
regenerating the lockfile, which still said 1.3.0. Any `uv run` syncs it. Pre-existing
drift, unrelated to these changes, probably wants its own commit.

## The Rust port changes the picture

Checked GitHub on 2026-08-30 before recommending any branch strategy.

**Issue #121 has not been started.** jjcfrancisco commented "I'll be looking at this soon"
on 2026-08-27; there is no branch for it. Remote branches are `main` and `rust` only.

**But there is a draft Rust port of the entire generator** — [PR #119](https://github.com/OvertureMaps/stac/pull/119),
+5232/-4107 across 49 files, closing #100, marked "Do not merge yet". It **deletes**
`src/overture_stac/overture_stac.py` and replaces it with Rust plus thin Python bindings.
It claims roughly 4x the speed of the Python implementation.

**The port reproduces every gap, including #121.** From `src/stac/theme.rs` on the `rust`
branch:

```rust
// Build Collection with extent from item bboxes (matches pystac's SpatialExtent(bboxes=[...])).
let extent = Extent {
    spatial: SpatialExtent {
        bbox: items.iter().filter_map(|it| it.bbox.as_ref().cloned()).collect(),
```

The comment is the tell — the bug is being carried forward deliberately, because the port
was written to match pystac's existing behaviour. The same file also has:

| | `rust` branch |
|---|---|
| `collection.title` | `Some(type_name.clone())` — raw slug |
| `table:columns` | `json!({"name": n})` — name only, no type |
| `providers` | absent |
| `keywords` | absent |
| item link titles | absent |

A `grep` across the whole branch finds no `provider` or `keyword` at all.

**What follows from this.** The Python hygiene changes are still worth landing: Python is
what generates the live catalog today, and #119 explicitly says not to merge yet. But the
five changes are also a checklist for the port, and #121 in particular is heading for a
rewrite that replicates it. Whether to fix it in Python, in Rust, or in both is
Francisco's call — he should just be making it knowingly.

Caveat: the `rust` branch was last updated 2026-08-27 and is in flux, so this reading may
be stale by the time anyone acts on it. Only `theme.rs` was examined closely.

## Open questions for the group

1. **Is the Portolan profile something Overture wants?** This is a policy call, not a code
   fix. Adopting it means the generator emits and publishes ~44 markdown files plus styles and
   thumbnails for 15 collections, and the publish workflow ships them. That's a real
   commitment to maintain.

2. **Who writes the column descriptions?** 217 columns across the full catalog. The 63 done
   here came from Overture's own schema reference, which covers places and buildings well. The
   rule followed throughout: a column left undescribed is a smaller failure than a column
   described wrongly.

3. **Where do the small STAC fixes land — Python, Rust, or both?** Link titles,
   human-readable titles, `table:columns` types, `providers`, and `keywords` are
   uncontroversial and independent of the Portolan question. They are written against the
   Python generator and pass its full test suite. The Rust port would need the same five
   changes. See the Rust port section above.

4. **`places` licence.** Currently `other`. Deliberately not changed — licence is a field the
   skill says to confirm with the publisher rather than research.

5. **Points get no legend.** The Portolan browser derives a legend only from a `fill` layer
   whose `fill-color` is a `match` or `step` expression. Places are points, so their styles
   render but produce no legend. That's a browser limitation worth raising upstream at
   `portolan-browser`.

## Reproducing this

```bash
# toolchain
uv venv portolan-venv
uv pip install --python portolan-venv/bin/python 'rashid>=0.1.8,<0.2.0' stac-check portolan-cli

# mirror the live catalog (rashid needs local files)
python3 mirror.py

# audit
python3 audit.py          # field-presence counts across all 15 collections
python3 bbox.py           # confirms issue #121 across 11 of 15

# build and validate the demo
python3 build_demo.py     # metadata + documented columns
python3 gen_docs.py       # README.md + AGENTS.md
python3 add_styles.py     # MapLibre styles as assets
python3 verify_queries.py # runs all 14 AGENTS.md queries against live data

portolan-venv/bin/rashid check --no-data --summary demo/catalog.json

# generator changes, in the stac repo
uv run pytest -q                              # 32 unit tests
uv run python tests/setup_test_catalog.py     # builds against real S3
uv run pytest -q                              # 62 tests, e2e now included
rashid check --no-data --summary tests/data/2026-08-19.0/catalog.json
```

Scripts live in the session scratchpad; they're throwaway quality but they document exactly
what was measured.
